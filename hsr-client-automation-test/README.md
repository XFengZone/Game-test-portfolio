# 崩坏：星穹铁道 · 客户端自动化测试

基于 **Airtest + OpenCV + PaddleOCR + WASAPI** 的游戏客户端自动化测试实践，覆盖**帧率档位**、**音量设置**与**开拓力数值**三项游戏内功能的验证。

核心思路：**用 UI 自动化驱动游戏设置，再通过观测实际输出（屏幕数值 / 音频电平）做统计断言** —— 观测玩家实际感知的输出，而不是游戏内部状态。

---

## 测试用例

| 用例 | 验证目标 | 观测手段 | 判定依据 |
|---|---|---|---|
| **帧率档位验证**<br>`test_change_fps` | 切换 60/30 帧后，实际帧率是否与标称一致 | 截图 + OCR 读取屏幕帧率显示 | 动作期间连续采样（约 30+ 次，间隔 0.15s），取中位数 ±10% |
| **音量设置验证**<br>`test_change_voice` | 音量档位变化后，实际输出电平是否同步变化 | WASAPI Loopback 录制系统音频 | 音量 0 ≤ -55dBFS；0→10 动态范围 ≥25dB；响度随档位单调递增 |
| **开拓力数值校验**<br>`test_01_single_consume` | 完成一次副本后，开拓力是否精确减少副本消耗量 | 打开详情面板 + 锚点定位 + OCR 读取「当前持有」数值 | 消耗前 − 消耗后 = 副本消耗量，允许 −1 的恢复误差 |

帧率用例通过 `pytest.mark.parametrize` 参数化，一组代码覆盖两个档位，在报告中呈现为两条独立用例：

```
test_change_fps[60帧档位]
test_change_fps[30帧档位]
```

## 核心实现

### 1. 帧率读取：从屏幕观测实际帧率

```
第三方帧率 OSD 叠加显示 → 截取游戏窗口 → 裁剪帧率数字区域
→ 按饱和度过滤彩色数字 → 放大 4 倍 → OCR → 清洗为整数
```

> 游戏客户端本身不显示帧率，帧率数值由第三方 OSD 工具绘制在窗口顶部后读取。

**关键设计**

- **用饱和度而非色相做颜色过滤**：帧率数字会随达标情况变色（跑满 60 帧显示绿色，未跑满显示黄色）。若按「黄色」过滤，会漏掉绿色的 60，导致采样到的全是掉帧数据、中位数被压低。两者的共同点是**高饱和度**，而 `FPS`/`CPU` 等标签是灰白色（低饱和），因此用 HSV 饱和度通道可同时保留两种数字、排除标签干扰。
- **裁剪 + 放大 4 倍**：整屏 OCR 实测 11.16 秒，裁剪到数字区域并放大后仅 0.59 秒，速度提升 19 倍，识别置信度达到 1.0。
- **采样取中位数而非平均值**：帧率存在偶发抖动，中位数对单个异常值零敏感，但持续偏低仍会暴露。实测样本 `[60×5, 59×5]`，中位数 59.5。
- **后台线程采样 + 主线程执行动作**：若先采集再移动，只能测到静止场景的帧率，而静止时帧率通常很稳、测不出问题。改为后台线程持续截图、主线程同时执行移动动作后，采样覆盖整个移动过程，能捕捉场景加载与资源流式加载这些真正容易掉帧的时刻。采样数与动作时长绑定，实测约 30+ 次。
- **采集与识别解耦**：截图约 50ms、OCR 约 600ms。截图线程只负责采集，识别统一放在动作结束、采样停止之后 —— 若边截边识别，采样间隔会被慢操作从 0.15 秒拖到 0.65 秒以上。

### 2. 音量验证：从系统音频流观测实际输出

```
WASAPI Loopback 录制系统输出 → 切分 50ms 窗口 → 计算每窗 RMS → 取峰值窗口 → 转 dBFS
```

**关键设计**

- **WASAPI Loopback 而非麦克风**：采集系统正在播放的音频流本身（与 OBS「桌面音频」同原理），不受环境噪声影响，测的是游戏实际输出的电平。
- **取峰值窗口而非整段平均**：2.5 秒录音中实际发声仅约 0.5 秒，整段平均会被静音段稀释。切成 50ms 窗口取最大值，保证发声被完整捕获（实测主峰落在 1400ms 处，与动作时序吻合）。50ms 这个窗口长度是两侧约束的结果：太短会量到瞬时振幅而非响度，太长会把静音段混进来。
- **后台线程录音 + 主线程执行动作**：录音接口是阻塞的，顺序执行会使动作发生在录音结束之后。通过线程让两者时间重叠，保证声音落在采集窗口内。
- **跨档位相对关系断言，而非绝对阈值**：不同场景的背景音乐强度不同，绝对电平会漂移 5~8 dB。判据采用同一次运行内三档位的相对关系，换场景、换机器依然成立。

**判定依据设计**

| 判据 | 阈值 | 实测值 | 防御的缺陷类型 |
|---|---|---|---|
| 动态范围 ≥ 25 dB | 25 dB | 148 dB | 音量滑条完全失效（此时三档同值，范围趋近 0） |
| 音量 0 ≤ -55 dBFS | -55 dBFS | -160 dBFS | 总音量未覆盖某个音源（如 BGM 未被静音） |
| 单调性 0 < 5 < 10 | — | 成立 | 档位映射错乱 |

阈值均为**倒推设定**：先确定目标缺陷会使数值变为多少，再将阈值置于「正常值」与「故障值」之间。三条判据刻意设得宽松，定位是捕获「功能失效」类缺陷，而非验证音量曲线的精确性 —— 收紧阈值会带来误报，而误报会让整套自动化失去信任。

### 3. 开拓力校验：锚点定位 + 结构校验

```
点击主开拓力图标 → 打开详情面板 → 以「当前持有：」为锚点模板
→ 右边缘向右裁剪 → 饱和度过滤出黄色数字 → 放大 → OCR → 字符纠正 → 三重校验
```

**关键设计**

- **从详情面板读，而不是主界面 HUD**：HUD 上的数字字号小、紧挨图标与「/ 上限」、且右对齐会随位数左右漂移，固定 ROI 必然在某个位数上失效。详情面板里字号更大、背景干净，数字是黄色，与灰色标签、白色背景形成明显对比 —— **换一个更容易观测的界面，比死磕原位置的裁剪参数更省事**。
- **锚点定位**：标签「当前持有：」固定不变，而数字位数会变（1~3 位）。取锚点矩形的右上、右下两个角点，得到右边缘与上下边界，再从右边缘向右按三位数宽度裁剪。**用不变的东西定位会变的东西**。
- **饱和度过滤**：数字是黄色（高饱和），标签灰色、背景白色（都低饱和）。亮度上前两者都很亮、分不开；饱和度上差异明显。
- **字符纠正**：OCR 可能把 `0` 读成 `O`。若直接过滤非数字字符，`"9O"` 会被静默过滤成 `"9"` —— 数值错了但测试不报错。因此先做 `O→0`、`I/l→1` 的纠正，再过滤。
- **图标歧义处理**：主开拓力与后备开拓力的图标结构相同（同款银环 + 同款星形），灰度匹配对两者的置信度都在 0.98 左右，会误点左侧的后备图标。改用 `match_all_in` 取全部匹配、按 x 排序取最右侧 —— **两者唯一稳定可区分的特征是位置，而位置比颜色稳定**。

**判定依据设计**

| 判据 | 设定 | 防御的缺陷类型 |
|---|---|---|
| 消耗差值 = 副本消耗量 | 允许 −1 | 开拓力每 6 分钟恢复 1 点，一次副本可能正好跨过恢复点 |
| 读数位数 ≤ 3 | — | 上限 300 点，超过三位必然是误读 |
| 读数在 0~300 之间 | — | 超出范围判定为读取失败，而不是让错误数值进入断言 |
| 连续两次读数一致 | 最多重试 4 次 | 挡住偶发 OCR 误读（开拓力 6 分钟才变，0.3 秒内两次应完全相同） |

**关于恢复计时的取舍**：开拓力的差值断言不能写成精确等于消耗量。测试跑一次副本约几分钟，期间可能正好跨过一次恢复点，导致差值比预期少 1。**若不允许这 1 点误差，用例会随执行时机随机失败，而且失败间隔刚好是 6 分钟的整数倍，极难排查。**

### 4. 框架组织：fixture 分级与状态管理

**三级 session 级 fixture**（整个测试会话只执行一次），统一处理所有用例共用的前置：

| fixture | 职责 |
|---|---|
| `airtest_device` | 连接游戏窗口 |
| `normalized_window` | 固定窗口尺寸与位置，保证 ROI 坐标稳定 |
| `warm_up_ocr` | 预热 OCR 模型，避免 4~5 秒的初始化耗时计入首条用例 |

**function 级 fixture** 负责状态复位，保证用例之间互不污染：

- 用例结束前把帧率与音量恢复到基线（帧率 60 / 音量 10）
- 复位前先判断当前状态，已在基线则跳过，避免每条用例都白进设置页
- 复位动作包在 `try/except` 内且不向上抛出 —— **teardown 抛异常会覆盖掉用例本身的失败信息**

**参数化与 fixture 的交互**：参数化的每个取值在 pytest 中都是独立用例，因此 function 级 fixture 会对每条各执行一遍完整的「前置 → 用例 → 后置」。这也保证了帧率两个档位的用例互相独立、一条失败不影响另一条执行。

### 5. 测试有效性验证（红灯测试）

自动化用例的价值取决于它**能否在缺陷发生时失败**。两条设置类用例均执行了反向验证：

- **帧率**：人为将游戏设为 30 帧后运行 60 帧断言，确认其正确失败并输出全部采样点
- **音量**：临时将动态范围阈值调至 200 dB，确认断言逻辑能正确计算差值并报错

开拓力用例的失败检出则依赖**数值层面的多重校验**：位数、范围、连读一致性 —— 任一项不满足都会判定读取失败并重试，而不是让一个错误数值流入断言。

### 6. 测试报告

集成 Allure，报告中每条用例附带：

- **实测数据**：帧率采样点与中位数、音量三档位响度曲线与判定明细
- **失败截图**：通过 `pytest_runtest_makereport` 钩子在用例失败时自动截图并附到对应用例

## 实测数据

**帧率（游戏窗口 1600×900）**

```
[FPS] 60帧档位 -> 中位数 59.5
[FPS] 30帧档位 -> 中位数 30.0
```

**音量**

```
[VOL] 音量-响度曲线:
      音量  0 ->  -160.0 dBFS
      音量  5 ->  -17.1 dBFS
      音量 10 ->  -11.9 dBFS
      动态范围(0 -> 10): 148.1 dB
```

> 音量 0 档为数字静音（-160 dBFS，float32 精度极限），因此 0→10 的 148 dB 反映的是「有信号与无信号」的差距，而非可听音量范围。真实可比的两档之间，5 档与 10 档实测相差 5.2 dB。

**开拓力**

断言形式为：`消耗前 − 消耗后 ∈ {副本消耗量, 副本消耗量 − 1}`

其中 −1 的容差用于覆盖 6 分钟一次的恢复计时。

## 缺陷定位记录

### OpenCV 多版本共存导致特征点匹配在原生层崩溃

**现象**：自动化用例在模板匹配失败时崩溃，报错 `cv2.error: Unknown C++ exception from OpenCV code`，异常穿透 `exists()` 掀翻整个测试进程。

**定位过程**

1. 崩溃栈指向 `SIFTMatching.get_keypoints_and_descriptors()` —— 模板匹配失败后，Airtest 自动降级到特征点匹配算法
2. `cv2.__version__` 报告 5.0.0，但 `BRISK_create` / `AKAZE_create` / `KAZE_create` 全部缺失 —— 完整的 OpenCV 5.0 不可能缺少这些函数
3. 检查已安装包，发现 `opencv-python`、`opencv-python-headless`、`opencv-contrib-python` **三个包共存于同一虚拟环境**

**根本原因**：三个包都提供 `cv2` 模块并写入同一目录，后安装者覆盖前者的 DLL，导致 Python 层与原生 DLL 版本不一致，SIFT 在原生层访问非法内存。

**为何异常会穿透捕获**：Airtest 的 `Template._try_match()` 只捕获自定义的 `aircv.BaseError` 子类，而 OpenCV 抛出的 `cv2.error` 不继承该基类，因此直接向上传播。而 Airtest 默认策略 `CVSTRATEGY = ["mstpl", "tpl", "sift", "brisk"]` 在模板匹配失败时会自动降级到 SIFT，从而触发这条崩溃路径。

**修复**

1. 卸载全部三个 OpenCV 包，统一安装 `opencv-contrib-python==4.10.0.84`（同时满足 PaddleOCR 底层 `paddlex` 的版本约束）
2. 配置 `ST.CVSTRATEGY = ["mstpl", "tpl"]` —— 除修复环境外，同时从策略上放弃特征点兜底。因为特征点匹配在 UI 模板失效时可能「模糊命中」错误位置，导致 `touch()` 点击到非预期区域，比测试失败更危险
3. **回归验证**：用当初触发崩溃的相同条件复现（模板匹配必然失败 → 触发降级），确认现在返回 `None` 而非崩溃，并附加正面对照确认匹配功能本身正常

### 主开拓力图标与后备开拓力图标匹配混淆

**现象**：点击开拓力图标时，实际点到了左侧的「后备开拓力」，打开的界面不对。

**定位过程**

1. 日志显示模板匹配置信度 `0.9816` —— 很高，说明匹配算法认为找到了
2. 对比两个图标：外框是同一个银灰色圆环，内部都是星形图案，**结构几乎一致，只有晶体颜色不同**
3. 灰度模板匹配只比较明暗分布，看不到颜色差异，因此对两者的置信度都在 0.98 左右

**为什么不用 `rgb=True`**：开启颜色匹配后置信度掉到 0.675 —— 图标尺寸仅 38×38，又带发光与抗锯齿，颜色本身就是最不稳定的特征。

**修复**：改用 `match_all_in` 取全部匹配结果，按 x 坐标排序取最右侧。主开拓力在右、后备在左，**位置是比颜色更稳定的区分特征**。

## 已知限制

- **帧率数值依赖第三方 OSD**：游戏客户端本身不显示帧率，需外部帧率显示工具处于开启状态。测试会话开始时会做一次可用性自检，未就绪时直接报出明确原因，避免后续识别失败被误判为坐标或配色问题
- **帧率 ROI 为固定坐标**：帧率数字区域依赖窗口尺寸与分辨率，更换环境需重新标定。改进方向是随窗口尺寸按比例换算，或先用 OCR 定位 `FPS` 标签再计算数字区域
- **开拓力读取依赖详情面板**：需先点开面板，比直接读 HUD 多一步交互。这一点可以接受 —— 开拓力 6 分钟才恢复 1 点，单条用例只需读两次
- **开拓力依赖 OCR 字符识别**：已通过字符纠正与三重校验兜底，但若字体或配色大幅变化，仍需重新标定饱和度阈值与锚点模板
- **用例依赖固定等待**：使用 `sleep` 而非条件等待，可改用 `wait(Template(...))` 缩短耗时
- **覆盖范围有限**：目前覆盖三项功能，后续将扩展至更多系统
- **依赖 PaddleOCR**：为读取数字引入了较重依赖，可评估替换为像素级数字模板匹配

## 合规说明

本项目**仅使用 UI 层截图匹配与输入模拟**：不读取游戏进程内存、不注入 DLL、不修改客户端文件、不篡改网络协议。音频采集使用系统级 WASAPI Loopback（等价于 OBS 桌面音频），不涉及游戏进程。

## 环境依赖

```
Python 3.12
airtest==1.4.3
opencv-contrib-python==4.10.0.84
paddleocr==3.7.0
paddlepaddle==3.3.1
soundcard
pytest
allure-pytest
numpy
```

**注意事项**

- `paddleocr` 需在导入前设置 `FLAGS_use_mkldnn=0`，否则会触发 oneDNN 后端的 `NotImplementedError`
- `airtest` 必须在 `soundcard` 之前导入，或统一设置 `sys.coinit_flags = 0`，避免 COM 线程公寓模式冲突
- 游戏窗口需固定尺寸（1600×900）并置于屏幕左上角，以保持模板匹配与 ROI 坐标的稳定性
- 帧率显示工具需处于开启状态，且帧率已叠加在游戏窗口上
- 运行音量验证前，需确认**系统播放音量处于正常水平且未静音**：
  回环采集的是系统播放流的电平，系统音量过低会压缩可测的动态范围，
  静音则会导致三档位全部测为数字静音。其余用例不受此影响

## 运行方式

```bash
# 运行全部用例
pytest

# 只跑帧率档位验证
pytest test_setting.py -k "change_fps"

# 只跑音量设置验证
pytest test_setting.py -k "change_voice"

# 只跑开拓力数值校验
pytest test_trailblaze_power.py
```

**生成 Allure 报告**

```bash
pytest --alluredir=report/allure-results --clean-alluredir
allure serve report/allure-results
```

`--clean-alluredir` 用于清空上一次运行的结果，避免多次运行的数据混在同一份报告中。
