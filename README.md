## 🚀 代码实践项目

### 1. 并发登录压力测试与 TCP 握手分析
**技术**：Python / Requests / Wireshark ｜ **目录**：`concurrent-login-test/`

- **场景**：模拟游戏开服或大版本更新时，大量玩家同时涌入登录。
- **实现**：用 `ThreadPoolExecutor` 模拟 100 个用户同时发起 POST 登录，统计成功率与响应时间分布；对比多进程与多线程在 IO 密集型任务下的表现差异。
- **网络分析**：结合 Wireshark 抓包，分析并发请求下的 TCP 三次握手过程，验证连接建立的可靠性。

### 2. 接口测试基础脚本
**技术**：Python / Pytest / Requests ｜ **目录**：`api-test-basics/`

- **场景**：日常接口回归测试。
- **实现**：GET/POST 请求发送、Cookie 登录态关联、JSON 响应断言。
- **进阶**：用 Pytest 组织用例，生成 Allure 测试报告。

### 3. 游戏客户端设置项自动化验证 —— 帧率档位与音量
**技术**：Airtest / OpenCV / PaddleOCR / WASAPI ｜ **目录**：`hsr-client-automation-test/`

- **场景**：验证游戏内设置项是否**真正生效**。「点了按钮」不等于「设置起效了」——本模块通过自动化驱动设置后观测实际输出，验证「设置 → 实际表现」这条完整链路。游戏环境为《崩坏：星穹铁道》PC 端，1600×900 窗口化。
- **帧率档位验证**：截图裁剪帧率数字区域 → 按 **HSV 饱和度**过滤彩色数字，兼容达标时绿色、未达标时黄色的双配色，同时排除灰白标签 → 放大 4 倍后 OCR 识别 → 10 次采样取中位数断言。设计上把采集与识别两阶段解耦，采样间隔由 0.65s 压缩至 **0.15s**；裁剪加放大后单次识别耗时从 11.16s 降至 **0.59s**，置信度 1.0。
- **音量设置验证**：通过 **WASAPI Loopback** 采集系统音频流，等价于 OBS 的桌面音频，不受环境噪声干扰 → 切分 50ms 窗口计算 RMS → 取峰值窗口转 dBFS；采用**后台线程录音 + 主线程执行动作**保证发声落在采集窗口内。实测 `音量0 = -160.0 / 音量5 = -17.1 / 音量10 = -11.9 dBFS`，动态范围 148.1 dB。
- **判定依据**：采用**跨档位相对关系断言**而非绝对阈值（动态范围 ≥25dB、音量0 ≤-55dBFS、响度单调递增）。不同场景 BGM 强度不同会使绝对电平漂移 5~8 dB，相对关系判据可跨场景、跨机器成立。阈值均为**倒推设定** —— 先确定目标缺陷会使数值变为多少，再将阈值置于正常值与故障值之间。
- **测试有效性验证**：两条用例均执行**红灯测试**。帧率用例人为将游戏设为 30 帧后运行 60 帧断言，确认其正确失败并打印全部采样点；音量用例临时调高阈值，确认断言能正确计算差值并报错。**一个从不失败的测试等于没有测试。**
- **进阶**：记录并定位了一个环境级缺陷 —— 三个 OpenCV 包共存导致 DLL 覆盖，使特征点匹配在原生层崩溃并穿透 `exists()` 掀翻整个测试；通过统一 `opencv-contrib-python==4.10.0.84` 修复，并将 `CVSTRATEGY` 收窄为纯模板匹配，最后用原始触发条件做回归验证。

## 📋 测试设计与文档

### 1. 草原核溢出链专项测试
**目录**：`dendro-core-overflow/`

- **立论**：从 177 条系统级用例中识别出一条「规则已知、结算口径未知」的路径 —— 场上满 5 颗草原核时，第 6 颗生成会强制引爆最早一颗，游戏内无任何提示。
- **方法**：拆解为 6 项待验证假设，设计 11 条专项用例并执行 9 条，全程录屏取证。
- **结论**：溢出伤害按核创建者属性结算，与创建者偏差 0.0%、与触发者相差 82.9%，双向排除触发者归属。
- **产出**：测试方案、执行记录表、测试报告。

### 2. 游戏核心系统测试用例库
**目录**：`game-core-test-design/`

- **30 条核心用例**：覆盖《原神》祈愿与元素反应、《崩铁》差分宇宙，按状态时序、数值、数据一致性、概率统计、功能、异常容错六类风险组织。
- **177 条完整回归库**：三大系统全量用例，另含《蓝色星原：旅谣》二测的 12 条缺陷、2 条回归闭环、8 条优化建议。
- **筛选逻辑**：30 条不是按编号截取，而是按「能发现什么级别的缺陷」重排；原始库 P0 占 66%，精选后 P0 占 30%。
